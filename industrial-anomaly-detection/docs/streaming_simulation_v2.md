# Потоковая симуляция transformer_mixed v2

Запускать команды из корня `industrial-anomaly-detection`. Симуляция читает CSV построчно, без предварительного построения всех окон. Она загружает сохранённые модель, scaler и порог и не обучается/не калибруется заново.

## Короткая демонстрация с предупреждением

```powershell
.\.venv\Scripts\python.exe -m src.simulate_transformer_mixed --start-row 176 --max-rows 160 --speed 10 --print-every 30
```

Участок выбран из ранее оценённого test2 для демонстрации вывода предупреждения, не для оценки качества. Первая строка — исходная запись с индексом 176 (отсчёт с нуля, заголовок не учитывается). После 30 warmup-записей начинается классификация. Speed 10 задаёт паузу 0.1 секунды между соседними секундными записями; время вычислений добавляется, поэтому это приближённое ускоренное воспроизведение, не hard real-time.

Для воспроизведения без ожидания:

```powershell
.\.venv\Scripts\python.exe -m src.simulate_transformer_mixed --max-rows 1000 --speed 0
```

Для всей записи с исходным секундным темпом:

```powershell
.\.venv\Scripts\python.exe -m src.simulate_transformer_mixed --speed 1
```

Полный test2 содержит 153000 записей; speed 1 воспроизводит около 42.5 часов исходной шкалы, плюс вычисления. Для короткой демонстрации задавать max-rows. Ctrl+C завершает воспроизведение с записью summary и сохранением уже обработанной истории.

## Артефакты и входы

По умолчанию используются:

- `artifacts/hai/transformer_mixed/mixed_v2_full_seed42_run1/` — лучший checkpoint эпохи 18 из прерванного после 22 эпох обучения; preprocessing v2 и сохранённый порог 0.1558542103.
- `data/raw/hai/holdout/test2.csv` — входной файл.
- `results/hai/streaming/<simulation-name>/` — отдельный каталог результата. По умолчанию имя создаётся автоматически из UTC-времени; существующий каталог не перезаписывается.

Другие файлы/имена задаются через `--input-file`, `--run-name`, `--simulation-name`. Для CLI доступны также `--quiet`, `--threads`, `--print-every`, `--start-row`, `--max-rows`, `--speed`; справка — `python -m src.simulate_transformer_mixed --help`.

Вход: CSV с разделителем `;`, столбцом `time` формата YYYY-MM-DD HH:MM:SS и 59 именованными каналами исходной схемы HAI. Метки attack/attack_P1/P2/P3 могут присутствовать, но исключаются перед передачей наблюдения детектору. Они не используются ни для score, ни для предупреждений. Заголовок проверяется на обязательные и дублированные поля.

При загрузке проверяются хэши модели и preprocessing относительно сохранённого порога. Другой scaler/порог не подставляется автоматически. Интерфейс StreamingDetector.push принимает одно наблюдение без необходимости иметь ground truth.

## Как принимается решение

1. Получить одно новое наблюдение t и проверить его формат/время/значения.
2. Преобразовать 55 числовых каналов сохранённым scaler; четыре булевых сохранить 0/1.
3. Если в буфере меньше 30 прошлых наблюдений — WARMUP, без фиктивного Normal.
4. Спрогнозировать t только из 30 предыдущих наблюдений. Текущее наблюдение ещё не находится в истории модели.
5. Рассчитать score = mean numeric MSE + mean binary CE. ANOMALY тогда и только тогда, когда score > saved threshold; иначе NORMAL.
6. Добавить текущее наблюдение в буфер для следующего шага.
7. Записать результат в predictions.csv; при ANOMALY также в alerts.csv и вывести WARNING.

Предупреждение означает превышение порога модели, а не подтверждённую кибератаку. Последовательные аномальные наблюдения дают отдельные строки alerts; группировка их в инциденты пока не выполняется.

При положительном разрыве времени буфер сбрасывается, и с текущей валидной записи начинается новый warmup. Невалидный timestamp, дубликат/обратный ход времени, отсутствие/NaN/Inf признака или булево значение вне {0,1} дают INSUFFICIENT_DATA, очищают историю и не превращаются в NORMAL. Следующий валидный участок требует нового warmup. Заполнение из будущих строк не применяется.

## Выходные файлы

- `predictions.csv`: каждая обработанная запись, включая WARMUP и INSUFFICIENT_DATA; event_id, исходный timestamp, status, prediction, score, numeric_mse, binary_ce, threshold, history_size, processing_ms, detail.
- `alerts.csv`: те же поля только для ANOMALY, включая уникальный в пределах файла ID исходной строки.
- `run_config.json`: пути, хэши входа/модели/порога, параметры запуска, происхождение модели.
- `summary.json`: completed/interrupted_by_user/failed/no_rows_processed, число строк и статусов. Создаётся также при остановке или ошибке обработки.

CSV-журналы сбрасываются через flush после каждой записи, чтобы их можно было читать во время воспроизведения. Это не гарантия сохранности при внезапном отключении питания. Processing_ms измеряет обработку, модель и решение, исключая ожидание и запись файлов; он не заменяет end-to-end benchmark из ТЗ.

## Проверка

Тесты покрывают причинное окно, точное правило порога, warmup, разрывы времени, неверные состояния, игнорирование разметки, CSV-предсказания/предупреждения и отказ от перезаписи результата. На 300 реальных test-целях проверено совпадение с сохранёнными пакетными решениями; scores сравниваются с atol=1e-5, rtol=1e-4 из-за различий batch=1 и batch=256.

Это программное воспроизведение записанных данных. MQTT, чтение реальных устройств/PLC и dashboard остаются отдельными этапами.
